# 実装計画 - Michael Jackson Footsteps Beat Trainer（iPhone版）

## 前提（ヒアリング結果）
- 開発機材：Mac無し。Windows PCのみ。実機テストは自分のiPhoneで行う。
- 予算：クレカ登録不要・無料の範囲で完結（Apple Developer Program(年間$99)には加入しない）。
- 技術方針：企画書に忠実なネイティブSwift/SwiftUIを採用（案A）。
- ビルド：GitHub Actions（macos-latestランナー、無料枠）でxcodebuild。
- 実機配布：AltStore/SideStore（無料Apple ID・クレカ不要）でサイドロード。AltServerはWindows対応なので、初回ペアリングも今のPCで完結する（Mac借用は不要）。
- MVP範囲：最小構成。①曲読み込み ②簡易BPM/拍検出 ③拍に合わせて振動 ④画面に足跡アイコン表示（なぞり判定なし）。指の追従判定・結果表示・モード切替・ARモードは後日追加。

## 方針転換（2026-08-04）
- 曲の読み込み方式を変更：端末のミュージックライブラリから都度選ぶ方式（`MPMediaPickerController`）を廃止し、**楽曲データをアプリのビルドに内蔵（バンドル）する方式**に切り替えた。
- 理由：ユーザーがPCでダウンロードした楽曲ファイルを直接アプリに組み込みたいという要望のため。個人の端末で個人が使う範囲を前提とする（企画書のUXステップ2「個人的に所持している曲を読み込む」に合致）。
- 受け渡しフロー：ユーザーが `inbox/music/` に楽曲ファイル（mp3/m4a/wav/aac）を配置 → Claudeが `Resources/Music/` に取り込み → `project.yml` のフォルダ参照経由でXcodeビルドに自動的に含まれる。
- 現状（このコミット時点）：`Resources/Music/` はまだ空。ユーザーからの楽曲提供待ち。
- 運用方針：実機（AltStoreインストール・ハプティクス/同期の体感確認）でのチェックは毎サイクル必須にせず、**コード実装 → GitHub Actionsのビルド成功確認**を基準に次のフェーズへ進めてよいと合意済み。実機での最終確認はユーザーが都合の良いタイミングでまとめて行う。

## マイルストーン

### Phase 0：環境・パイプライン構築（最優先）
- Windows PCにAltServerをインストールし、無料Apple IDでペアリング
- iPhoneにAltStore（またはSideStore）をインストール
- GitHub ActionsでXcodeプロジェクトをビルドし、unsigned .ipaを生成するワークフローを作成
- ビルド→AltStore経由で実機インストールまでの一連の流れを、空のSwiftUIアプリで疎通確認

### Phase 1：ハプティクス動作確認
- UIImpactFeedbackGenerator/CHHapticEngineで単発振動を実機で鳴らす
- Phase 0のパイプラインで最新ビルドが実機に届くことを再確認

### Phase 2：曲読み込み（内蔵方式に変更済み）
- `Resources/Music/`（Xcodeフォルダ参照）にバンドルした楽曲ファイルを、アプリ起動時に列挙するUIを実装
- 選択した曲をAVAudioEngineで再生できることを確認

### Phase 3：拍（ビート）検出
- 選択した曲の波形をオフラインで解析し、拍のタイムスタンプ配列を生成
- エネルギーピーク検出などの簡易アルゴリズムで実装（本格的なBPM解析ライブラリは使わず、割り切った精度で進める）

### Phase 4：ハプティクス同期再生
- 拍タイムスタンプに合わせてCHHapticEngineの振動イベントを事前スケジューリング
- 曲の再生時刻とハプティクスのタイミングを同期させる

### Phase 5：足跡アニメーション（なぞり判定なし）
- SwiftUIで足跡アイコンが拍に合わせて画面上を動くアニメーションを実装
- ここまででMVP v1完成

### Phase 6（任意・後日）
- 指のなぞり追従判定（タッチ座標・速度・タイミング解析）
- 結果フィードバック画面（精度％、ズレ傾向、コメント）
- モード切替（ビート重視／ステップ重視／観賞モード）
- ARモード（床に足跡投影）

## リスク・技術的な懸念点
1. **著作権・配布範囲**：内蔵する楽曲はAI生成による、営利目的以外では自由に使える音源（ユーザー確認済み・2026-08-04）。市販曲の著作権リスクはないため、公開リポジトリへのコミットも問題ない。
2. **BPM/拍検出の精度**：専用ライブラリを使わない簡易実装のため、複雑な楽曲では検出精度が落ちる可能性がある。MVPでは精度より「拍に合わせて振動する」体験の成立を優先する。
3. **AltStore/SideStoreの運用コスト**：無料Apple IDでの署名は7日で失効するため、定期的な再署名（SideStoreならWi-Fi/VPN経由で自動化可能、AltStoreなら都度PCとの接続が必要）が発生する。開発中はこの再インストール作業が頻発する前提で運用フローを組む。
4. **GitHub Actionsのビルド時間**：privateだと実質月200分程度に制限されるため、**publicリポジトリで進める方針に決定済み**（ソースコード公開について合意済み）。

## Phase 2 進捗（内蔵方式へ再実装済み・2026-08-04）
- `project.yml`：`Resources/Music`をフォルダ参照（`type: folder`, `buildPhase: resources`）としてターゲットに追加。`NSAppleMusicUsageDescription`は不要になったため削除
- `Resources/Music/`：アプリに内蔵する楽曲の実体置き場（現在は空、ユーザーからの提供待ち）
- `inbox/music/`：ユーザーが楽曲ファイルを一時的に置く受け渡し場所（README.txt に運用手順を記載）
- `Sources/HisFootsteps/BundledSongLibrary.swift`：Bundle内の`Music`フォルダを走査し、内蔵曲一覧（`BundledSong`）を返す新規ロジック
- `Sources/HisFootsteps/AudioPlayerManager.swift`：`MPMediaItem`ベースの読み込みを廃止し、`BundledSong`（ローカルバンドルURL）を読み込むように変更
- `ContentView.swift`：MPMediaPickerControllerのシート表示を廃止し、内蔵曲一覧から選んで再生するUIに変更
- `Sources/HisFootsteps/MediaPicker.swift`は`archive/Sources_HisFootsteps/`へ退避（削除はせず保管）
- `.github/workflows/build.yml`：曲ファイル追加時もCIが走るよう、pathsトリガーに`Resources/**`を追加

## Phase 3 進捗（実装済み・ビルド未確認・2026-08-04）
- `Sources/HisFootsteps/BeatDetector.swift`：曲の波形をオフラインで解析し、拍タイムスタンプ配列と推定BPMを返すロジックを新規実装
  - アルゴリズム：1024サンプル単位のウィンドウでエネルギー（二乗平均）を計算し、直近約1秒分（43ウィンドウ）の平均エネルギーの1.3倍を超えた瞬間を拍と判定する簡易エネルギーピーク検出方式
  - 連続検出を防ぐため拍と拍の最小間隔を0.2秒（300BPM相当が上限）に設定
- `ContentView.swift`：選択曲に対して「拍を解析」ボタンを追加。バックグラウンドスレッドで解析を実行し、完了後に推定BPMと検出拍数を表示

## Phase 4 進捗（実装済み・ビルド未確認・2026-08-04）
- `HapticsManager.swift`：`playBeatPattern(beatTimestamps:)`を追加。拍タイムスタンプ配列を1つの`CHHapticPattern`（各拍を`relativeTime`付きの`hapticTransient`イベントとして）にまとめて事前スケジューリングし、`start(atTime: CHHapticTimeImmediate)`で再生。`stopBeatPattern()`で途中停止も可能
- `ContentView.swift`：拍検出済みのとき「ビートに合わせて再生」ボタンを追加。押下時に`playBeatPattern`呼び出し直後に`player.play()`を呼ぶことで音楽とハプティクスの再生開始タイミングを近づける簡易同期を実装（フレーム精度の同期は狙わず、割り切った精度で実装。企画書のリスク許容方針に沿う）
- 「停止」ボタンで音楽・ハプティクス両方を停止するよう変更

## 既知の課題：push・CI確認がブロック中
- このセッションの環境（Claude Codeのシェルプロセス）から`git push`/`git fetch`が`getaddrinfo() thread failed to start`エラーで失敗し続けている（`ping`でのGitHub到達性は正常なため、DNSではなくスレッド生成に関する既知のWindows Git不具合の可能性が高い）。
- ユーザーが別ターミナルから`git push`を試みた際も、GitHub Actions側で新しいワークフロー実行が作成されていないことをAPI(`/repos/.../actions/runs`)で確認済み＝pushがGitHubまで到達していない可能性が高い。
- そのため、Phase 2（内蔵方式移行）・Phase 3（拍検出）ともに**GitHub Actionsでのビルド成功はまだ未確認**。ユーザーの判断で「今は緊急対応不要」として実装を優先する方針で進めている。
